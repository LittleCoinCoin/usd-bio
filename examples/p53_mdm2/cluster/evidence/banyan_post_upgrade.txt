SINGULARITY INTERPRETATION
Two things changed and one thing did not.

Changed (1): the runtime resolved by a bare `singularity` is no longer the
4.2.2 module build under /opt but a distro package, singularity-ce
4.5.0-noble at /usr/bin/singularity. `dpkg -l` shows it as an installed
package and `buildcfg` reports PREFIX=/usr, so this is the noble package and
not a hand-built tree. The campaign's delivered gromacs.sif was written by
4.2.2 (its own label records
org.label-schema.usage.singularity.version: 4.2.2), so any rebuild started
today from a default PATH would use a DIFFERENT writer than the one whose
output dgx1 has been verified against.

Changed (2): `module` no longer loads anything by default. The prior campaign
record describes 4.2.2 as a default-loaded module; here `module list` reports
"No Modulefiles Currently Loaded" and the module is not visible at all from a
non-login sh, which is the shell an `ssh banyan '<cmd>'` invocation gets.

Not changed: /opt/singularity/4.2.2 survived the upgrade intact and
`module load singularity/4.2.2` still resolves to it and still reports
"singularity-ce version 4.2.2". The exact writer that produced the verified
artifact is therefore still available on the machine. This is the cheapest
possible mitigation for the gzip guard and it requires no build to confirm --
only that a rebuild explicitly load the module instead of trusting PATH.

COMPRESSOR EVIDENCE INTERPRETATION -- READ HONESTLY
What is [observed]:
  * singularity-ce 4.5.0-noble is the default runtime, and it calls out to the
    system /usr/bin/mksquashfs 4.6.1 rather than compressing in-process.
  * /etc/singularity/singularity.conf exposes mksquashfs path, procs and mem.
    It exposes NO compressor or algorithm key. An administrator cannot pin the
    compressor from this config file.
  * `singularity build --help` and `man singularity-build` expose no
    --compress / --compression flag and document no default algorithm. The
    only occurrence of the word is the prose "The compressed Singularity read
    only image format (default)", which names a format, not an algorithm.
  * No SINGULARITY_* environment variable is set that could override it.
  * The `-comp` literal and the compressor names lz4/lzo do exist inside the
    4.5.0 binary, and a source path
    internal/pkg/util/fs/squashfs/mksquashfs_singularity.go is named in it.

What is NOT observed, and must not be reported as if it were:
  * The DEFAULT COMPRESSOR FOR A NATIVE SIF BUILD IS UNDETERMINED BY THIS
    CAPTURE. The `-comp` token and the algorithm names appear in the binary
    but never adjacent to one another, because Go concatenates string
    literals; nothing here shows which value 4.5.0 passes to mksquashfs, nor
    whether it passes `-comp` at all rather than accepting the mksquashfs
    built-in default. The gzip/zstd hits that DO carry clear context all
    belong either to vendored Go libraries or to the OCI-SIF blob compressor
    (blobcompress.gzipAlgo / blobcompress.zstdAlgo), which is the --oci code
    path and not the native squashfs path this campaign uses.
  * Reading a compressor off the version number alone would be inference, not
    observation, and is deliberately not done here.

The only way to settle it is to build one small image and run `unsquashfs -s`
on it. That is a mutation and is therefore PI-attended under Q-006; this unit
stops here by design.

GZIP GUARD STATUS: STILL LIVE, and its premise is now confirmed rather than
speculative. The writer HAS changed (4.2.2 -> 4.5.0-noble) while the dgx1
reader is unchanged at 3.5.2, which is exactly the skew the guard was written
to catch. What has ALSO changed is the cost of failure: because
/opt/singularity/4.2.2 survived and its modulefile still loads, a rebuild can
simply pin the old writer if the new one turns out to emit something dgx1
cannot mount. The guard is a check to run, not a risk to fear.

DOCKER INTERPRETATION -- THE COLD-CACHE GATE
The PI's hypothesis that a rebuilt /var/lib/docker would have taken the image
and cache state with it is FALSIFIED. `docker system df` reports 52 images
totalling 213.3 GB and 108 build-cache records totalling 16.46 GB -- the same
16.46 GB figure recorded before the upgrade. Cache records are dated "4 months
ago" and "2 weeks ago", i.e. they predate the upgrade. /var/lib/docker survived.

Consequences for the cold-cache rebuild gate:
  * The gate is NOT free. A rebuild started today would still hit a warm
    cache, so a genuine cold-cache rebuild must force it explicitly
    (--no-cache, or a scratch DOCKER_* root) rather than relying on the
    upgrade having cleared it. The caveat on manifest seq 3 -- that build
    equivalence was measured against CACHED compile layers -- therefore still
    stands unresolved.
  * The 179.9 GB reclaimable is unchanged and remains available, which is why
    the root filesystem is still at 52% (Section 6). No disk-pressure reason
    to prune, and pruning is a mutation this unit does not perform.
  * The gromacs-p53mdm2 image itself is absent, consistent with its deletion
    in convert_verify step 5 (manifest seq 3) rather than with any upgrade
    effect. Both nvidia/cuda base images are still cached.

Docker itself was upgraded alongside the OS: engine 29.7.2 built 2026-08-05,
containerd v2.3.3, nvidia runtime 1.4.3, storage driver overlay2 on xfs. The
`docker images` output format also changed in this CLI generation (DISK
USAGE / CONTENT SIZE columns), which is why `docker images | wc -l` (24, tagged
only, plus header) and `docker system df` Images (52, all) disagree; `docker
images -a | wc -l` is 53 = 52 + header, and 29 of the 52 are dangling.
